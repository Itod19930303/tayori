## 1. 背景

現在、利用者向けの日本語メッセージ文言が各画面・コンポーネント・ライブラリにハードコードで散在している。特に以下の重複・不整合リスクがある。

- 「このアルバムへのアクセス権がありません。管理者に招待を依頼してください。」が **3ファイル**（アルバム詳細 / 権限管理 / メディアプレビュー）に同一文言で重複。
- 「保存に失敗しました。時間をおいて再試行してください。」が **2ファイル**（アルバム作成 / 権限管理）に重複。
- 「アルバムが見つかりません。」が **2ファイル**に重複。
- 文言を1箇所直しても他箇所が取り残され、UI表記ゆれが発生しうる。テストも各ファイルで文字列をハードコードしており、文言変更時の追随コストが高い。

基本設計書 8.1 でエラー文言は一覧管理する方針が示されているが、実装レベルの単一の情報源（Single Source of Truth）が存在しない。

## 2. 目的

利用者向けメッセージ文言を `src/lib/messages/` 配下の定数ファイルに一元集約し、以下を達成する。

- 同一文言の重複を単一定数に統合し、表記ゆれと修正漏れを構造的に排除する。
- 文言変更を1箇所の編集で完結させ、テストも定数importで追随できるようにする。
- 将来の `window.confirm` 系文言（`confirmMessages.ts`）の受け皿を型定義レベルで用意する。
- provider設計（[基本設計書 5.3]）と同様、「変更理由が単一のもの」を1箇所へ寄せる development.md の共通化方針に沿う。

## 5. データ設計（定数ファイルの型・キー一覧）

### 5.1 配置

`src/lib/messages/` に3ファイルを新設する。既存の `src/lib/`（`auth.ts` / `validators.ts` 等）と同階層で、Firebase 非依存の純粋モジュールとする。

```
src/lib/messages/
  errorMessages.ts     # ERROR_MESSAGES（エラー・警告・403/404・バリデーション）
  successMessages.ts   # SUCCESS_MESSAGES（成功トースト・完了バナー）
  confirmMessages.ts   # CONFIRM_MESSAGES（window.confirm 系の受け皿・空実装）
```

### 5.2 `errorMessages.ts`

キーは `オブジェクト形式`（`ERROR_MESSAGES.KEY`）。静的文言は `string`、パラメータを含むものは `(引数) => string` の**関数形式**。

## 6. 命名規則・パラメータ付きメッセージのルール

以下を明文化し、今後の追加時も統一する。

### 6.1 命名規則

- **オブジェクト形式**で定義し、`ERROR_MESSAGES.FORBIDDEN` のようにドット参照する（PM確定仕様）。
- 定数オブジェクト名は `SCREAMING_SNAKE_CASE` の複数形（`ERROR_MESSAGES` / `SUCCESS_MESSAGES` / `CONFIRM_MESSAGES`）。
- キー名は `SCREAMING_SNAKE_CASE`。意味ドメインが明確な場合はプレフィックスを付ける（`AUTH_`, `EMAIL_`, `UPLOAD_`, `MEDIA_`）。
- キー名は「文言そのもの」ではなく「使われる状況・意味」を表す（例: 文言が変わっても `FORBIDDEN` というキーは維持できる）。
- オブジェクトは `as const` を付け、値をリテラル型に固定する（誤代入防止・型補完）。

### 6.2 パラメータ付きメッセージ（関数形式）

- 文字列補間を含む文言は `(引数) => string` の**関数形式**で定義する（PM確定仕様）。
- 引数は意味の分かる名前・型を付ける（`(max: number)`, `(count: number)`）。
- 呼び出し側は `ERROR_MESSAGES.TITLE_MAX_LENGTH(TITLE_MAX)` のように引数を渡して評価する。
- 上限値（`TITLE_MAX=50` 等）は呼び出し側（`validators.ts`）が保持し、メッセージ関数へ引数として渡す。**マジックナンバーをメッセージ定義側に埋め込まない**（文言と業務ルール値の責務を分離するため）。

### 6.3 静的 / 関数の使い分け

| 種別 | 定義 | 例 |
|---|---|---|
| 静的（補間なし） | `string` | `FORBIDDEN: '…'` |
| パラメータ付き（補間あり） | `(arg) => string` | `TITLE_MAX_LENGTH: (max: number) => \`…${max}…\`` |

## 8. `POST_FORBIDDEN` 統合可否の最終判断

**判断: `FORBIDDEN` とは統合せず、別キー `POST_FORBIDDEN` として独立させる。**

### 根拠

| 観点 | `FORBIDDEN` | `POST_FORBIDDEN` |
|---|---|---|
| 文言 | このアルバムへのアクセス権がありません。管理者に招待を依頼してください。 | 投稿権限がありません。 |
| 発生条件 | **非メンバー**（`memberUids` に自分が含まれない）による閲覧アクセス（403相当） | **メンバーだが `canPost === false`**（閲覧はできるが投稿不可） |
| 対象画面 | アルバム詳細 / 権限管理 / メディアプレビュー（閲覧系3画面） | アップロード画面のみ |
| 利用者への意味 | そもそもアルバムを見られない | 見られるが、この操作（投稿）だけできない |

development.md「共通化の判断チェックリスト」に照らすと、

1. 入出力の型: 両方 string で一致するが、
2. **エラー処理の方針が異なる**（非メンバーの完全遮断 vs メンバーの部分制限）、
3. **変更トリガーが異なる**（招待導線の文言を直す理由 vs 投稿権限UIの文言を直す理由は別イベント）、
4. **含む業務ルールが異なる**（メンバーシップ判定 vs `canPost` 権限判定）。

チェックリスト2〜4を満たさないため「同じ意図」ではなく、**統合しない**（デフォルトNo側）。文言も実際に異なるため、無理に共通化すると片方の文言変更が他方へ意図せず波及するリスクがある。よってPM推奨（別キー維持）を採用する。

## 9. `getAuthErrorMessage` 型「関数内文字列のみ置換」パターンの扱い

`src/lib/auth.ts` の `getAuthErrorMessage(code)` は、Firebase 認証エラーコードを日本語へ変換する**分岐ロジックを持つ関数**である。この関数自体は定数化の対象外とし、**関数はそのまま残し、内部の文字列リテラルのみを `ERROR_MESSAGES` 参照へ置換する**。

### 方針

- 関数のシグネチャ・分岐構造（`switch`）・`popup-closed-by-user` の `''` 返却は**変更しない**（テスト `AU-05〜08` / `LP-06〜09` の挙動を維持）。
- `case` 内の return 文字列のみを定数参照へ置換する。

置換イメージ（before / after）:

```typescript
// after（分岐・空文字返却はそのまま、文言だけ定数参照へ）
export function getAuthErrorMessage(code: string): string {
  switch (code) {
    case 'auth/popup-closed-by-user':
      return '' // 空文字（UI非表示）は文言ではないため定数化しない
    case 'auth/network-request-failed':
      return ERROR_MESSAGES.AUTH_NETWORK_FAILED
    case 'auth/too-many-requests':
      return ERROR_MESSAGES.AUTH_TOO_MANY_REQUESTS
    default:
      return ERROR_MESSAGES.AUTH_SIGNIN_FAILED
  }
}
```

### 一般化ルール

「エラーコード→文言変換」や「状態→文言選択」のように**分岐ロジックを内包する関数**は、関数を定数ファイルへ移さず呼び出し元（`auth.ts` 等）に残す。定数ファイルは**文言（データ）のみ**を持ち、**どの文言を選ぶかの判断（ロジック）は持たない**。これにより定数ファイルは Firebase 非依存の純粋データモジュールを維持でき、テストも文言比較のみで完結する。`validators.ts` も同様（検証ロジックは `validators.ts` に残し、文言のみ `ERROR_MESSAGES` を参照）。

## 11. エラー処理

本タスクは「文言の置き場所」を変えるリファクタリングであり、**表示される文言の値・タイミング・条件は一切変えない**。

| 想定リスク | 対応 |
|---|---|
| 置換ミスで文言が変わる | 定数の値を旧文言と**完全一致**で定義（末尾の句点「。」有無まで一致）。テスト `MSG-*` で値を固定し、既存表示テストは定数importで二重に担保 |
| キー参照の綴り間違い | `as const` + TypeScript のプロパティ参照で存在しないキーはコンパイルエラー |
| 関数形式の引数漏れ | `TITLE_MAX_LENGTH` 等は引数必須の関数型。引数無し呼び出しは型エラー |
| 成功/失敗の tone 取り違え | エラーは `ERROR_MESSAGES`、成功は `SUCCESS_MESSAGES` とファイル分離し責務を明示 |

削除操作は行わない（既存ローカル定数の削除はファイル削除ではなくコード置換であり、restrictions.md の「ファイル・DB削除」には該当しないが、置換であっても影響レポートを提示する）。

## 12. 権限

本タスクはUI文言の内部管理方式の変更であり、**利用者の権限（viewer/editor/admin/owner）による挙動は変更しない**。`FORBIDDEN`（非メンバー）・`POST_FORBIDDEN`（`canPost===false`）・権限管理画面の `canManage` ガード等の**権限判定ロジックは一切変更しない**（文言の参照先のみ変更）。権限別の表示文言は従来どおり。

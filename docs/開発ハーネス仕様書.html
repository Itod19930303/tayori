1. ハーネスの全体構成

本プロジェクトは Claude Code のサブエージェント機能を用い、PM → writer → developer → ソースコードレビュワー → 仕様レビュワー → 総合レビュワー の6役割で開発を進める。 各役割の振る舞いは .claude/agents/*.md にエージェント定義として、 一連の流れは .claude/commands/workflow.md にスラッシュコマンド /workflow として定義されている。プロジェクト共通の方針は CLAUDE.md（リポジトリ直下）と .claude/rules/*.md に分割して管理する。

設計上のポイント: レビュー工程は「コード品質」「仕様適合性」「セキュリティ/性能/回帰」の3観点に 分離されており、各レビュワーは自分の担当観点以外を検査対象から明示的に除外する。 これにより指摘の重複や責任の曖昧化を防いでいる。

2. エージェント一覧

以下は .claude/agents/ 配下に定義された6エージェント。tools は利用可能なツール、model は使用モデルを示す。

tools: Read, Glob, Grep, TodoWrite / model: sonnet

pm — プロジェクトマネージャー

要件（目的・対象範囲・制約・完了条件・影響範囲）の整理、各役割へのタスク割振り、品質ゲート判定、最終報告の作成を担う。全工程の起点と終点。

tools: Read, Glob, Grep, Write, Edit / model: opus

writer — 設計担当

設計書（データ設計・処理フロー・エラー処理・権限・完了条件）とテスト仕様書（正常系/異常系/境界値/権限/回帰の5観点）を作成。実装都合の差分が出た場合はドキュメントを更新する。

tools: Read, Glob, Grep, Write, Edit, Bash, PowerShell, TodoWrite / model: opus

developer — 実装担当

テストコードを先に作成し失敗を確認してから実装するTDDを徹底。カバレッジ90%以上を目標とし、未達時は理由・リスク・追加方針をPMへ報告する。

tools: Read, Glob, Grep, Bash, PowerShell / model: sonnet

code-quality-reviewer — ソースコードレビュワー

ネストの深さ・可読性・命名・デッドコード・重複・メソッド粒度・責務分離・テスト容易性・Next.js規約など、コードの技術的品質のみを検査する。仕様適合性は対象外。

tools: Read, Glob, Grep / model: sonnet

spec-reviewer — 仕様レビュワー

実装・テストコードが設計書/テスト仕様書/完了条件と乖離していないかのみを検査する。コードの可読性等の技術品質は対象外。

tools: Read, Glob, Grep, Bash, PowerShell / model: sonnet

reviewer — 総合レビュワー

ソースコードレビュワー・仕様レビュワーの結果を踏まえ、セキュリティ・パフォーマンス・回帰影響を検査したうえで最終合否を判定する。

3. ワークフロー（/workflow）

/workflow <タスク> で起動すると、以下の10ステップで進行する。

1
PM

要件確認

目的・背景・対象範囲/対象外・制約・完了条件・影響範囲を整理し、曖昧な点はユーザーへ確認する。

2
writer

設計書作成

対象機能/画面/API・データ設計・処理フロー・エラー処理・権限・影響範囲・完了条件を、developerが迷わない粒度で作成。

3
writer

テスト仕様書作成

正常系・異常系・境界値・権限・回帰の5観点を必ず含める。

4
developer

テストコード作成（先行・Red確認）

実装前にテストを書き、まず失敗することを確認してから次工程へ進む（TDD）。

5
developer

実装（Green/Refactor）

  • 既存の構成・命名・テストフレームワークに従う
  • 共通化できる処理は共通化する（影響範囲が広い場合はPMへ確認）
  • 設計書との差分が出た場合はwriterへドキュメント修正依頼
  • Next.js実装は .claude/rules/nextjs-conventions.md に従う
6
developer

テスト実行・カバレッジ確認

カバレッジ目標90%以上。未達の場合は現在値・未達理由・リスク・追加テスト方針をPMへ報告。

7
code-quality-reviewer

コード品質レビュー

ネスト深さ・可読性・命名・デッドコード・重複/共通化・責務分離・テスト容易性・Next.js規約を検査。NGはdeveloperへ差し戻し、再度Step 7を実施。

8
spec-reviewer

仕様適合性レビュー

設計書どおりの対象範囲/データ設計/処理フロー/権限か、テスト仕様書5観点の充足、完了条件の達成を検査。

9
reviewer（総合）

最終レビュー

セキュリティ・パフォーマンス・回帰影響を検査。Step 7/8にNGがあれば集約してPMへNG報告。3者すべて承認で合格。

10
PM

最終確認

実施内容・変更ファイル・テスト結果/カバレッジ・レビュー結果・残課題/リスク・次の提案をまとめてユーザーへ報告。

4. 差戻しルール

各レビュワーがNG判定を出す場合は、以下の項目を明示したうえで担当へ差し戻す。

項目内容
依頼先PM / writer / developer のいずれか
該当箇所ファイルパス:行番号（仕様レビューは対応する設計書/テスト仕様書の該当箇所も併記）
問題何が問題か
理由なぜ修正が必要か
期待する修正どう直すべきか
確認方法修正後に何を確認するか

判断基準: 仕様・設計の問題は writer、実装・テストの問題は developer、スコープ・判断の問題は PM へ。

5. 実装・設計ルール（.claude/rules/）

5.1 development.md — 実装ルール

項目内容
TDD設計書・テスト仕様書 → テストコード（Red確認） → 実装（Green） → リファクタリング。テストフレームワークはVitest + React Testing Library、カバレッジ目標90%以上
共通化の判断基準「重複回数」ではなく「同じ意図（同じ理由で変更されるか）」で判断。4項目チェックリスト（入出力の型/エラー処理方針/変更トリガー/業務ルールの有無）をすべて満たす場合のみ共通化。重要処理は2箇所目、一般処理は3箇所目（Rule of Three）が目安。迷ったら共通化を見送る
関数定義スタイルトップレベルの関数（Reactコンポーネント本体・カスタムフック・src/lib/の公開関数等）はfunction宣言。内部のコールバック等はアロー関数でよい
実装コメントファイル/クラス/関数単位で「何を・なぜ」実装したかを記載。TODOや一時的なメモは残さない（判断経緯はPR説明等コード外に記録）

5.2 atomic-design.md — コンポーネント設計ルール

層判定基準
atomsこれ以上分解すると意味を失う最小単位。ビジネスロジックを持たない（shadcn/ui生成物もここ）
moleculesatomsの組み合わせで1つの意味的単位。propsのみで完結（データ取得しない）
organisms独立したUIセクション。ローカルstateは可だがFirestore/Storageへの直接アクセス禁止
templatesorganismsを配置したレイアウト骨格。実データを持たない
pages（page.tsx）hooks/経由で実データを取得し、templateへpropsとして渡す

ドメイン別フォルダ（album/ 等）は採用せず、配置判断は常にAtomic Designの階層のみで行う。

5.3 nextjs-conventions.md — Next.js実装規約

項目原則本プロジェクトの例外
フォントnext/font/googleを使用（CDN直読み禁止）Material Symbols等の可変フォントで非対応の場合はコードコメントで明記して例外扱い
読み込み/エラー表示loading.tsx/error.tsx/not-found.tsxのファイル規約に従う403/404はデータ依存のビジネスロジック判定のため、既存のNoticeScreen出し分けパターンを踏襲してよい
Server/Client Components可能な箇所はServer Componentsでデータ取得Firebase Auth/Firestoreのリアルタイム購読に依存するため、page.tsxはすべて'use client'を許容
画像表示next/imageを使用Firebase Storageの署名付きURLを表示する箇所（AlbumCard/MediaCell/UploadItem等）と外部プロフィール画像は<img>を許容

例外に該当しない新規コードでの違反（未使用のnext/font/google、独自スピナー実装、根拠コメントのないnext/image不使用、安易な'use client'）はdeveloperへの差戻し対象。

6. 制約・禁止事項（restrictions.md）

Git push / fetch 禁止 — git push・git fetch・gh pr create/merge/release は料金発生のため、ユーザーの明示的指示なしに実行しない（git pull は可）。
削除操作禁止 — ファイル・ブランチ削除、git reset --hard/git clean -f、DB/Storageの削除APIは、対象・理由・影響範囲を提示してユーザー確認を取ってから実行する。
依存関係確認手順 — ソースコード修正前に「変更対象の特定 → 依存関係の調査 → 影響範囲の報告」を行う。影響が広い場合は事前にリグレッションテスト計画をユーザーと合意する。

# Claude Code 開発チーム運用指示書

作成者: **Manus AI**  
用途: **Claude Codeに読み込ませる開発運用プロンプト / 指示書**

## 1. このドキュメントの目的

このドキュメントは、Claude Codeで開発作業を行う際に、**PM、writer、developer、レビュワー**の4つのサブエージェント役割を起動し、設計、テスト仕様、TDD実装、レビュー、修正依頼、最終確認までを一貫して進めるための指示書です。

Claude CodeにこのMarkdownを読み込ませた後は、単にコードを書くのではなく、**PMが全体統制を行い、writerが設計書とテスト仕様書を作成し、developerがテストコード作成後に実装し、レビュワーが成果物を検査する**という流れで作業してください。

## 2. 基本方針

すべての開発作業は、**要件確認、設計、テスト仕様、テストコード作成、実装、レビュー、最終確認**の順で進めてください。実装を急がず、先に期待動作を明文化してください。

特にdeveloperは、writerが作成した設計書とテスト仕様書をベースに作業してください。実装前にテストコードを作成し、その後に実装を行ってください。カバレッジは原則として**90%以上**を目標にしてください。

ただし、既存プロジェクトにテスト基盤がない場合、外部サービス依存が強い場合、UI自動テストが困難な場合など、90%に到達できない合理的な理由がある場合は、未達理由、リスク、追加すべきテスト方針をPMへ報告してください。

## 3. サブエージェント構成

| エージェント | 役割 | 主な成果物 |
|---|---|---|
| PM | 全体統制、最終確認、各エージェントへのタスク割り振り、品質ゲート判定 | 作業計画、タスク割当、最終判定、リスク整理 |
| writer | 各設計書の作成、テスト仕様書の作成、実装差分に応じたドキュメント修正 | 要件定義、基本設計、詳細設計、テスト仕様書、変更履歴 |
| developer | writerが作成した設計書とテスト仕様書をベースに、テストコード作成後に実装する。共通化できるものは共通化し、必要に応じてwriterへドキュメント修正依頼を行う | テストコード、実装コード、共通部品、テスト結果、カバレッジ結果 |
| レビュワー | 作成された成果物をレビューし、NGの場合は各エージェントへ修正依頼を行う | レビュー結果、指摘一覧、承認/差戻し判定 |

## 4. 各エージェントの詳細指示

### 4.1 PM

PMは、すべての作業の起点と最終確認を担当してください。ユーザーの依頼を読み、目的、対象範囲、制約、完了条件、影響範囲を整理してください。

曖昧な点があり、実装判断に影響する場合は、作業前にユーザーへ確認してください。質問せずに進められる場合は、仮定を明示したうえで作業を開始してください。

PMは、writer、developer、レビュワーへタスクを割り振ってください。作業が小さい場合でも、最低限、writer相当の仕様確認、developer相当の実装、レビュワー相当の検査を行ってください。

PMは最終的に、完了条件、変更内容、テスト結果、カバレッジ、レビュー結果、残課題、リスクを確認し、ユーザーへ報告してください。

### 4.2 writer

writerは、PMが整理した要件をもとに、設計書とテスト仕様書を作成してください。

設計書には、対象機能、画面またはAPI、データ構造、状態管理、エラーハンドリング、権限、影響範囲、完了条件を含めてください。developerが迷わず実装できる粒度で記述してください。

テスト仕様書には、正常系、異常系、境界値、権限、回帰確認の観点を含めてください。

developerから、共通化、実装都合、設計変更、仕様補足に関するドキュメント修正依頼があった場合は、設計書とテスト仕様書を更新してください。ドキュメントと実装を乖離させないでください。

### 4.3 developer

developerは、writerが作成した設計書とテスト仕様書を確認し、まずテストコードを作成してください。可能な限り、先に失敗するテストを書き、その後に実装してテストを通してください。

実装は、既存プロジェクトの構成、命名規則、設計思想、テストフレームワークに従ってください。既存コードの流儀を無視して新しい書き方を持ち込まないでください。

実装中に共通化できる処理、重複、責務過多、型定義の整理、命名改善を発見した場合は、必要に応じて共通化してください。ただし、仕様外の大規模変更はPMへ確認してください。

共通化や実装判断によって設計書またはテスト仕様書に差分が出た場合は、writerへドキュメント修正依頼を出してください。

テスト実行後は、結果とカバレッジをPMへ報告してください。カバレッジは90%以上を目標とし、未達の場合は理由と追加テスト方針を明記してください。

### 4.4 レビュワー

レビュワーは、作成された設計書、テスト仕様書、実装コード、テストコード、テスト結果をレビューしてください。

レビューでは、仕様適合性、テスト妥当性、実装品質、責務分離、共通化、命名、可読性、保守性、セキュリティ、パフォーマンス、既存機能への影響を確認してください。

NGの場合は、どのエージェントへ戻すべきかを明確にしてください。仕様や設計の問題はwriterへ、実装やテストの問題はdeveloperへ、スコープや判断の問題はPMへ修正依頼してください。

## 5. 標準ワークフロー

### Step 1: PMによる要件確認

PMは、ユーザー依頼から以下を整理してください。

| 項目 | 確認内容 |
|---|---|
| 目的 | 何を達成する作業か |
| 背景 | なぜ必要か |
| 対象範囲 | どこまで対応するか |
| 対象外 | 今回やらないこと |
| 制約 | 技術、期限、既存仕様、運用上の制約 |
| 完了条件 | 何をもって完了とするか |
| 影響範囲 | 既存機能や関連ファイルへの影響 |

### Step 2: writerによる設計書作成

writerは、以下の形式で設計書を作成してください。

| 項目 | 内容 |
|---|---|
| 背景 | なぜこの機能または修正が必要か |
| 目的 | 何を達成するか |
| 対象範囲 | どこまで対応するか |
| 対象外 | 今回やらないこと |
| 画面/API | 対象となる画面、コンポーネント、API |
| データ設計 | 型、DB、状態、保存先 |
| 処理フロー | 入力から出力までの流れ |
| エラー処理 | 想定される失敗と対応 |
| 権限 | 誰が何をできるか |
| 影響範囲 | 既存機能への影響 |
| 完了条件 | 何をもって完了とするか |

### Step 3: writerによるテスト仕様書作成

writerは、以下の形式でテスト仕様書を作成してください。

| テスト種別 | 観点 | 例 |
|---|---|---|
| 正常系 | 期待どおり動くか | 入力後に保存される |
| 異常系 | エラー時に壊れないか | 不正入力でエラー表示される |
| 境界値 | 最大値・最小値で問題ないか | 文字数上限、ファイルサイズ上限 |
| 権限 | 許可された人だけ操作できるか | 非ログイン時はアクセス不可 |
| 回帰 | 既存機能が壊れていないか | 既存テストが通る |

### Step 4: developerによるテストコード作成

developerは、実装前にテストコードを作成してください。既存のテストフレームワークがある場合は、それに従ってください。

テストコードを作成したら、必要に応じて一度テストを実行し、期待どおり失敗することを確認してください。これは、テストが実装前の未対応状態を正しく検出できているかを確認するためです。

### Step 5: developerによる実装

developerは、テストが通るように実装してください。実装中に共通化できる処理があれば共通化してください。

ただし、共通化によって影響範囲が広がる場合は、PMに確認してください。実装結果が設計書やテスト仕様書と異なる場合は、writerへドキュメント修正依頼を出してください。

### Step 6: developerによるテスト実行とカバレッジ確認

developerは、実装後にテストを実行してください。可能であればカバレッジも計測してください。

カバレッジ目標は**90%以上**です。未達の場合は、以下を報告してください。

| 項目 | 内容 |
|---|---|
| 現在のカバレッジ | 計測できた数値 |
| 未達理由 | なぜ90%に届かないか |
| リスク | 未テスト部分にどのようなリスクがあるか |
| 追加テスト方針 | 何を追加すれば改善できるか |

### Step 7: レビュワーによるレビュー

レビュワーは、以下の観点でレビューしてください。

| 観点 | 確認内容 |
|---|---|
| 仕様適合性 | 設計書どおりに実装されているか |
| テスト妥当性 | テスト仕様書の観点が満たされているか |
| 実装品質 | 可読性、保守性、責務分離が適切か |
| 共通化 | 重複処理が適切に整理されているか |
| セキュリティ | 認証、権限、入力値、ファイル、外部APIの扱いが安全か |
| パフォーマンス | 不要な処理、過剰な再レンダリング、重い処理がないか |
| 回帰影響 | 既存機能が壊れていないか |

NGの場合は、以下の形式で修正依頼してください。

| 項目 | 内容 |
|---|---|
| 依頼先 | PM / writer / developer のいずれか |
| 問題 | 何が問題か |
| 理由 | なぜ修正が必要か |
| 期待する修正 | どう直すべきか |
| 確認方法 | 修正後に何を確認するか |

### Step 8: PMによる最終確認

PMは、レビュワーの承認後に最終確認を行ってください。完了報告では、以下を簡潔にまとめてください。

| 項目 | 内容 |
|---|---|
| 実施内容 | 何を行ったか |
| 変更ファイル | どのファイルを変更したか |
| テスト結果 | 実行したテストと結果 |
| カバレッジ | 数値、または未計測理由 |
| レビュー結果 | 承認、修正済み、残指摘 |
| 残課題 | 今後対応すべきこと |
| リスク | 注意すべき点 |
| 次の提案 | ユーザーが次に進めやすい行動 |

## 6. 品質ゲート

各フェーズの完了時に、以下の品質ゲートを確認してください。

| ゲート | 判定基準 |
|---|---|
| 要件ゲート | 目的、対象範囲、完了条件が明確である |
| 設計ゲート | developerが迷わず実装できる設計になっている |
| テストゲート | 正常系、異常系、境界値、権限、回帰の観点がある |
| 実装ゲート | テストコード作成後に実装している |
| カバレッジゲート | カバレッジ90%以上を目標にし、未達なら理由を記録している |
| 共通化ゲート | 重複処理や責務過多を必要に応じて共通化している |
| レビューゲート | レビュワーが承認、または指摘に対応済みである |
| 最終ゲート | PMが成果物、リスク、残課題を確認している |

## 7. 修正依頼ルール

修正依頼は、責任者、問題、理由、期待する修正、確認方法を明確にしてください。曖昧に「直して」と指示せず、どの成果物のどこをどう修正すべきかを示してください。

| 依頼先 | 依頼内容の例 |
|---|---|
| PM | スコープ調整、優先順位変更、仕様判断 |
| writer | 設計書修正、テスト仕様追加、変更履歴更新 |
| developer | 実装修正、テスト追加、共通化、バグ修正 |
| レビュワー | 再レビュー、観点追加、承認判断 |

## 8. 簡易モード

小さな修正では、すべての成果物を重く作らなくて構いません。ただし、役割の観点は省略しないでください。

| 作業規模 | 運用 |
|---|---|
| 小 | 設計メモ、確認観点、実装、セルフレビューで進める |
| 中 | 設計書、テスト仕様、実装、レビューを行う |
| 大 | フェーズ分割し、各フェーズでレビューとPM承認を行う |

## 9. 追加で重視すること

認証、権限、ファイルアップロード、外部API、課金、個人情報、セキュリティに関わる実装では、レビュワーが重点的に確認してください。

ユーザーが明示していない仕様でも、実務上危険な点があればPMがリスクとして報告してください。developerが実装中に設計と異なる判断をした場合は、writerへドキュメント修正依頼を出し、PMが最終的に整合性を確認してください。

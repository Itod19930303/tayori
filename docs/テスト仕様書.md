## 1. 文書概要

### 1.1 目的

本書は「たより」MVPの最初の実装単位である **共通基盤 + ログイン画面（画面1）** について、developerがTDD（[`.claude/rules/development.md`](../.claude/rules/development.md)）でそのまま着手できる粒度のテストケースを定義する。各ケースは「対象ファイル / テストの目的 / 前提条件（モックすべきFirebase SDK関数）/ 期待結果」を明記する。

### 1.2 対象範囲（今回の実装単位）

| # | ファイル | 役割 |
|---|---|---|
| 1 | `src/lib/firebase.ts` | Firebase初期化（app / auth / db / storage）|
| 2 | `src/types/index.ts` | `Album` / `AlbumMember` / `Media` / `UserProfile` 型 |
| 3 | `src/lib/auth.ts` | `signInWithGoogle()` / `signOutUser()` / `getAuthErrorMessage()` |
| 4 | `src/contexts/AuthContext.tsx` | `onAuthStateChanged` 購読、`{ currentUser, loading }` 提供 |
| 5 | `src/hooks/useAuth.ts` | `useContext(AuthContext)` ラッパー |
| 6 | `src/app/(auth)/login/page.tsx` | ログイン済みは `/` へredirect、未ログインは `LoginTemplate` 表示 |
| 7 | `src/components/templates/LoginTemplate.tsx` | ログイン画面レイアウト骨格 |
| 8 | `src/components/molecules/LoginCard.tsx` | ロゴ・サブテキスト・Googleログインボタン・エラー表示 |
| 9 | `src/middleware.ts` | pass-through（`NextResponse.next()` のみ）|

### 1.3 対象外

後続の画面（ホーム / アルバム詳細 / アップロード / 権限管理 / メディアプレビュー / アルバム作成）および、それらが利用する `firestoreAlbum.ts` / `firestoreMedia.ts` / `uploadFile.ts` / `mediaUrl.ts` / `validators.ts` / `useAlbum` / `useMediaList` は本書の対象外とする。ただし [5.2](#52-srctypesindexts型定義) と [5.4](#54-srccontextsauthcontexttsx認証状態プロバイダ) の回帰観点では、後続画面が同じ型・AuthContextを再利用できることを確認する。

> 上記整備自体は設計書 10.1 のディレクトリ構成・9.2 のテスト戦略に沿うものであり、新方式の持ち込みではない。設定ファイルの具体値はdeveloper判断とし、乖離が出た場合は本書へ追記する。

## 4. 共通モック方針

developerが各テストで再利用するモックの指針。実装詳細は任せるが、モック対象は本節に統一する。

### 4.1 `firebase/auth` のモック

```
vi.mock('firebase/auth', () => ({
  getAuth: vi.fn(() => ({ /* auth stub */ })),
  GoogleAuthProvider: vi.fn(),
  signInWithPopup: vi.fn(),
  signOut: vi.fn(),
  onAuthStateChanged: vi.fn(),
}))
```

- `signInWithPopup`: 成功時は `{ user: モックUser }` を resolve、失敗時は `{ code: 'auth/...' }` を持つエラーを reject させる。
- `onAuthStateChanged`: コールバックを保持し、テスト側から任意のタイミングで `User` または `null` を発火できるようにする。戻り値は unsubscribe 関数（`vi.fn()`）とする。

### 4.2 `firebase/app` / `firebase/firestore` / `firebase/storage` のモック

```
vi.mock('firebase/app', () => ({
  initializeApp: vi.fn(() => ({ /* app stub */ })),
  getApps: vi.fn(() => []),
  getApp: vi.fn(() => ({ /* app stub */ })),
}))
vi.mock('firebase/firestore', () => ({ getFirestore: vi.fn(() => ({})) }))
vi.mock('firebase/storage', () => ({ getStorage: vi.fn(() => ({})) }))
```

### 4.3 `next/navigation` のモック

```
const push = vi.fn()
vi.mock('next/navigation', () => ({
  useRouter: () => ({ push, replace: vi.fn() }),
  redirect: vi.fn(),
  useSearchParams: () => new URLSearchParams(''),
}))
```

### 4.4 モックUserの共通スタブ

```
const mockUser = {
  uid: 'test-uid',
  displayName: 'テスト太郎',
  email: 'test@example.com',
  photoURL: 'https://example.com/photo.png',
} as unknown as import('firebase/auth').User
```

### 5.1 `src/lib/firebase.ts`（Firebase初期化）

対象: Firebase Appの初期化と `auth` / `db` / `storage` のエクスポート。設計書 2.3（環境変数）/ 10.1 に準拠。

| ID | 種別 | 目的 | 前提条件（モック）| 操作 | 期待結果 |
|---|---|---|---|---|---|
| FB-01 | 正 | Firebase Appが `NEXT_PUBLIC_FIREBASE_*` 環境変数から初期化される | `firebase/app` の `initializeApp` をモック、`getApps` は `[]` を返す。`vi.stubEnv` で6つの環境変数を設定 | モジュールを import | `initializeApp` が、設定した `apiKey` / `authDomain` / `projectId` / `storageBucket` / `messagingSenderId` / `appId` を含むconfigで1回呼ばれる |
| FB-02 | 正 | `auth` / `db` / `storage` がエクスポートされる | `getAuth` / `getFirestore` / `getStorage` をモック | モジュールを import | `auth` / `db` / `storage` が `undefined` でなく、各getterが1回ずつ呼ばれる |
| FB-03 | 異 | 多重初期化を防ぐ（HMR/再import時に既存appを再利用）| `getApps` が既存app配列 `[app]` を返す | モジュールを import | `initializeApp` は呼ばれず `getApp()` の結果を使う（Firebase "app/duplicate-app" エラーを発生させない）|
| FB-04 | 異 | Firestore/Storageの初期化がAuthと独立していること（初期化失敗が連鎖しない設計の確認）| `getStorage` が例外を投げるようモック | モジュールを import | `auth` は正常に取得され、Storage初期化の失敗が `auth` 取得を妨げない（import順序・分離を検証）。※実装が単純な即時初期化の場合はこのケースをスキップ可とし、理由をPMへ報告 |

> 補足（異常系の扱い）: 設計書上、Firestore/Storageの初期化失敗はログイン画面の機能に直接影響しない（ログインは `auth` のみ使用）。FB-04はログイン機能が Firestore/Storage の初期化状態に依存しないことを担保するための回帰的チェックである。

### 5.2 `src/types/index.ts`（型定義）

対象: `Album` / `AlbumMember` / `Media` / `UserProfile`。設計書 5.1 のスキーマに完全準拠すること。ランタイムの振る舞いを持たないため、型レベルの検証（コンパイルが通ること）を中心にする。

| ID | 種別 | 目的 | 前提条件 | 操作 | 期待結果 |
|---|---|---|---|---|---|
| TY-01 | 回 | `Album` が設計書5.1の全フィールドを持つ | なし | 全必須フィールド（`albumId` / `title` / `ownerId` / `memberUids` / `members` / `mediaCount` / `createdAt` / `updatedAt`）と任意フィールド（`description?` / `coverImageUrl?`）を持つオブジェクトリテラルを型注釈付きで生成 | 型エラーなくコンパイルが通る（`vitest` 実行時に `tsc --noEmit` もしくは型付きテストで担保）|
| TY-02 | 回 | `AlbumMember` の `role` が `'owner' \| 'admin' \| 'editor' \| 'viewer'` に限定される | なし | `role: 'guest'` を代入したオブジェクトを用意 | 型エラーになること（`@ts-expect-error` で検証）。`canView` / `canPost` / `canManage` が `boolean` である |
| TY-03 | 回 | `Media` が `provider: 'firebase' \| 'cloudinary' \| 'mux'` を必須で持つ | なし | `provider` を省いた `Media` を用意 | 型エラーになること（`@ts-expect-error`）。将来のCloudinary/Mux移行に備えたフィールドが型に存在する（設計書5.3）|
| TY-04 | 回 | `UserProfile` が本人プロファイル用フィールド（`uid` / `displayName` / `email` / `photoURL?` / `createdAt` / `updatedAt`）を持つ | なし | 型注釈付きオブジェクトを生成 | 型エラーなくコンパイルが通る |
| TY-05 | 回 | `Timestamp` 型が `firebase/firestore` の `Timestamp` を参照している | なし | `createdAt` に `Timestamp` 型の値を代入 | 型整合。後続のFirestore CRUD実装で同一型を再利用できる |

> `@ts-expect-error` を用いる型テストは、Vitestの型チェック（`vitest --typecheck`）またはCIの `tsc --noEmit` で担保する。方式はdeveloper判断とし、選択結果を本書へ追記する。

### 5.3 `src/lib/auth.ts`（認証ラッパー）

対象: `signInWithGoogle()` / `signOutUser()` / `getAuthErrorMessage(code)`。設計書 6.1 / 8.3 に準拠。

#### 5.3.1 `signInWithGoogle()`

| ID | 種別 | 目的 | 前提条件（モック）| 操作 | 期待結果 |
|---|---|---|---|---|---|
| AU-01 | 正 | Googleログインが成功しUserを返す | `signInWithPopup` が `{ user: mockUser }` を resolve。`GoogleAuthProvider` をモック | `await signInWithGoogle()` | `signInWithPopup` が `auth` と `GoogleAuthProvider` インスタンスで1回呼ばれ、`mockUser` が返る（または void を返す設計なら例外を投げない）|
| AU-02 | 異 | ポップアップ多重呼び出しなどSDKエラーがそのまま伝播する | `signInWithPopup` が `{ code: 'auth/cancelled-popup-request' }` を reject | `signInWithGoogle()` | エラーが呼び出し元（page）へ throw される（`auth.ts` は握りつぶさず、メッセージ変換は `getAuthErrorMessage` の責務）|

#### 5.3.2 `signOutUser()`

| ID | 種別 | 目的 | 前提条件（モック）| 操作 | 期待結果 |
|---|---|---|---|---|---|
| AU-03 | 正 | サインアウトが実行される | `signOut` が resolve | `await signOutUser()` | `signOut` が `auth` を引数に1回呼ばれる |
| AU-04 | 異 | サインアウト失敗時にエラーが伝播する | `signOut` が reject | `signOutUser()` | エラーが throw される（呼び出し元でハンドリング可能）|

#### 5.3.3 `getAuthErrorMessage(code)` — 設計書8.3のマッピング完全一致

| ID | 種別 | 目的 | 入力 | 期待結果（戻り値）|
|---|---|---|---|---|
| AU-05 | 異 | ユーザー起因のキャンセルはメッセージ非表示 | `'auth/popup-closed-by-user'` | `''`（空文字）|
| AU-06 | 異 | ネットワーク失敗メッセージ | `'auth/network-request-failed'` | `'ネットワーク接続を確認してください。'` |
| AU-07 | 異 | リクエスト過多メッセージ | `'auth/too-many-requests'` | `'しばらく時間をおいてから再試行してください。'` |
| AU-08 | 異 | 未知コードはデフォルトメッセージ | `'auth/internal-error'`（任意の未定義コード）| `'Googleでログインに失敗しました。もう一度お試しください。'` |
| AU-09 | 境 | 空文字・undefined など想定外入力でもデフォルトへフォールバック | `''` / `undefined` | デフォルトメッセージを返す（例外を投げない）|

> AU-08の文言は設計書8.3の `default` 文言と一致させる。設計書本文では「Googleログインに失敗しました。もう一度お試しください。」と表記（8.1 #1）。実装文言は設計書8.3のコードブロックを正とし、差異があればレビューで統一する。

### 5.4 `src/contexts/AuthContext.tsx`（認証状態プロバイダ）

対象: `onAuthStateChanged` を購読し `{ currentUser, loading }` を提供する Context Provider。設計書 6.1 / 7.4 に準拠。

| ID | 種別 | 目的 | 前提条件（モック）| 操作 | 期待結果 |
|---|---|---|---|---|---|
| AC-01 | 境 | 初期値は `currentUser: null` / `loading: true`（ちらつき防止、設計書7.4）| `onAuthStateChanged` はコールバック未発火の状態 | `AuthProvider` で子をレンダリングし、初期のContext値を読む | `currentUser === null` かつ `loading === true` |
| AC-02 | 正 | ログイン済みユーザー検知で `currentUser` が設定され `loading: false` になる | `onAuthStateChanged` のコールバックに `mockUser` を発火 | 発火後にContext値を確認 | `currentUser === mockUser` かつ `loading === false` |
| AC-03 | 正 | 未ログイン確定時は `currentUser: null` / `loading: false` | `onAuthStateChanged` のコールバックに `null` を発火 | 発火後にContext値を確認 | `currentUser === null` かつ `loading === false`（AC-01との差は `loading` が確定済みである点）|
| AC-04 | 正 | セッション切れ（User→null）を検知して状態を更新する（設計書7.4）| 先に `mockUser` を発火、続けて `null` を発火 | 2回目発火後の値を確認 | `currentUser === null` に更新される |
| AC-05 | 正/回 | アンマウント時に購読解除する（メモリリーク防止）| `onAuthStateChanged` が unsubscribe 用 `vi.fn()` を返す | Providerをアンマウント | unsubscribe関数が1回呼ばれる |
| AC-06 | 回 | 提供する値の形が `AuthContextType`（`{ currentUser: User \| null; loading: boolean }`）と一致し、後続画面で再利用可能 | なし | Contextの型・キーを検証 | キーが `currentUser` と `loading` の2つのみで、設計書6.1の `AuthContextType` と一致（ホーム等の未ログインリダイレクト実装がこの形に依存できる）|

### 5.6 `src/components/molecules/LoginCard.tsx`

対象: ロゴ・サブテキスト・Googleログインボタン・エラー表示を持つ表示コンポーネント。Atomic Design上 molecules（propsのみで完結、Firebase/Storage直アクセス禁止 — [atomic-design.md](../.claude/rules/atomic-design.md)）。設計書 4.3 / 3.7 / 9.3 に準拠。

想定props（設計書4.3の状態を親から受け取る形）:

```
interface LoginCardProps {
  onSignIn: () => void
  isLoading: boolean
  error: string | null
}
```

| ID | 種別 | 目的 | 前提条件（モック）| 操作 | 期待結果 |
|---|---|---|---|---|---|
| LC-01 | 正 | アプリ名ロゴ「たより」とサブテキストが表示される | `onSignIn=vi.fn()`, `isLoading=false`, `error=null` | レンダリング | 「たより」および「LINEで流れてしまう画像・動画を、チームで一元管理。」が表示される |
| LC-02 | 正 | Googleログインボタンが表示され押下でコールバックが呼ばれる | 同上 | 「Googleでログイン」ボタンをクリック | `onSignIn` が1回呼ばれる |

## 7. カバレッジ方針

- 目標: 全対象ファイル合計で **90%以上**（設計書9.2）。
- カバレッジ計測が難しい箇所と方針:

| 箇所 | 難点 | 方針 |
|---|---|---|
| `firebase/auth` の `signInWithPopup` | 実ブラウザポップアップが必要 | `vi.mock()` で完全モック。E2E（後工程Playwright）でカバー（設計書9.2）|
| `firebase.ts` の実初期化 | 実際のFirebaseプロジェクト接続が必要 | SDKをモックし、config受け渡し・多重初期化防止のロジックのみ検証 |
| `middleware.ts` | Edge Runtime実行 | `NextResponse` をモックし関数単体で検証 |

- 90%未達となった場合は、現在値・未達理由・リスク・追加テスト方針をPMへ報告してから次工程へ進む（[development.md](../.claude/rules/development.md) 1章）。

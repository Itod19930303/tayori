# 実装ルール

コード実装時に守るべきルール。禁止・制約事項は [`restrictions.md`](restrictions.md) を参照。

## 1. テスト駆動開発（TDD）

実装前に必ずテストコードを作成し、**失敗することを確認してから**実装に着手する。

| ステップ | 内容 |
|---|---|
| 1 | 設計書・テスト仕様書をもとにテストコードを書く |
| 2 | テストを実行し、失敗（Red）することを確認する |
| 3 | テストを通す最小限の実装を行う（Green） |
| 4 | 必要に応じてリファクタリングする（Refactor） |

- テストフレームワークは既存踏襲（Vitest + React Testing Library）
- カバレッジ目標は90%以上（`CLAUDE.md` の品質基準を参照）。未達の場合は現在値・理由・リスク・追加テスト方針をPMへ報告する

## 2. 共通化の判断基準

同じ処理が複数ファイルで使用される場合、**「重複回数」ではなく「同じ意図（同じ理由で変更されるか）」**を基準に共通クラス・共通関数への切り出しを判断する。

### 判断チェックリスト

以下を**すべて満たす場合のみ**「同じ意図」と判定し共通化する。1つでも満たさない場合は共通化しない。

1. 入出力の型が同じ、または1〜2個のオプション引数で吸収できる
2. エラー処理の方針が同じ（同じ失敗ケースを同じ方法で扱っている）
3. 変更トリガーが同じ（「この処理を直す理由になりうる出来事」が両方の呼び出し元で重なる）
4. 業務ルールを含んでいない、または同一の業務ルールのみを含む

### 目安となるタイミング

| 処理の重要度 | 共通化を検討するタイミング |
|---|---|
| 認証・権限・ファイルアップロード・外部APIなど重要処理 | 2箇所目の重複時点 |
| その他一般処理 | 3箇所目の重複時点（Rule of Three） |

### 迷った場合

チェックリストで判断が割れる、または迷う場合は**共通化を見送る**（デフォルトNo側に倒す）。コード中にTODOコメント等の一時的なメモは残さず、判断の経緯はPR説明やレビューコメントなど**コード外**に記録する。

### 具体例

| 判定 | 例 | 理由 |
|---|---|---|
| 共通化してよい | `src/lib/mediaUrl.ts` の provider分岐 | Cloudinary/Mux移行という単一の変更理由を持つため |
| 共通化しない | フォームのバリデーションエラーメッセージ文言 | 画面ごとに文言・条件が変わりうるため |

### レビュー時の確認

developerが共通化を行った場合、チェックリスト1〜4のどれを満たしたかをレビュー時に明記し、レビュワーが機械的に検証する。影響範囲が広い共通化は `restrictions.md` セクション3の依存関係確認手順に従い、事前にユーザー/PMへ報告する。

## 3. 実装コメントのルール

すべての実装（ファイル・クラス・関数単位を基本とする）に、**「何を・なぜ実装したか」の概要と意図を説明するコメントを必ず記載する**。

- コメントには実装の背景（なぜこの処理が必要か）を含め、処理内容をそのまま言い換えただけの説明にはしない
- TODOコメントや一時的なメモ書きはコードに残さない。判断経緯はPR説明・レビュー記録に残す

> 注: `CLAUDE.md` のグローバル方針（コメントは基本書かず、WHYが非自明な場合のみ記載）は、本プロジェクトの実装コードに関してはこのルールが優先される。
